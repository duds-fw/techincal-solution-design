# 1. Purpose

This ADR documents the decision to adopt PostgreSQL as the primary relational database for the NexaPay Payment Platform.

---

# 2. Context

NexaPay requires a relational database for transactional data, merchant data, and reconciliation data.

**Requirements:**

- ACID compliance for financial transactions
- High availability
- Scalability to 10,000 TPS
- JSON support for flexible schemas
- Strong community and enterprise support
- Cloud-managed option available

**Existing Landscape:**

- No existing enterprise database standard
- Team has mixed PostgreSQL and MySQL experience
- AWS infrastructure (RDS available)

---

# 3. Decision Statement

> NexaPay will use PostgreSQL 16 as the primary relational database, deployed on Amazon RDS with Multi-AZ.

---

# 4. Decision Drivers

| Driver | Importance |
|--------|-----------|
| ACID Compliance | Critical |
| Performance | High |
| Scalability | High |
| JSON Support | Medium |
| Cloud Managed | High |
| Team Expertise | Medium |
| Cost | Medium |

---

# 5. Considered Options

| Option | Description |
|--------|-------------|
| PostgreSQL | Open-source, ACID, JSON support |
| MySQL | Open-source, widely used |
| Oracle | Commercial, enterprise features |
| Aurora PostgreSQL | AWS-managed PostgreSQL |

---

# 6. Evaluation

| Criteria | PostgreSQL | MySQL | Oracle | Aurora PostgreSQL |
|----------|-----------|-------|--------|-------------------|
| ACID | Yes | Yes | Yes | Yes |
| JSON Support | Excellent (JSONB) | Limited | Yes | Excellent |
| Scalability | Good | Good | Excellent | Excellent |
| Cost | Free | Free | High | Medium |
| Cloud Managed | RDS | RDS | RDS | Native |
| Team Expertise | Medium | Medium | Low | Medium |
| Community | Strong | Strong | Vendor | AWS |

---

# 7. Decision Rationale

PostgreSQL on RDS was selected because:

- Superior JSON support via JSONB for flexible schemas
- Strong ACID compliance for financial transactions
- Cost-effective (no license fees)
- RDS provides managed operations, backups, and failover
- Multi-AZ provides high availability
- Aurora PostgreSQL provides additional performance if needed

Trade-offs:

- Requires team upskilling from MySQL
- Some advanced features available in Oracle are not available

---

# 8. Consequences

**Positive:**

- Strong data integrity for financial transactions
- Flexible schema evolution via JSONB
- Lower licensing costs
- Managed operations via RDS

**Negative:**

- Team needs PostgreSQL training
- Some MySQL-specific queries need rewriting

**Future Implications:**

- May migrate to Aurora PostgreSQL for performance
- PostgreSQL will be the enterprise standard for new projects

---

# 9. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Team expertise gap | Medium | Training program |
| Performance at scale | Low | Aurora upgrade path |

---

# 10. Implementation Guidance

- Use Amazon RDS PostgreSQL 16
- Enable Multi-AZ for production
- Use connection pooling (PgBouncer)
- Implement database migrations via Flyway
- Enable pg_stat_statements for query monitoring
